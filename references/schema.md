# AGENTS.md / CLAUDE.md 通用模式模板

> 用于初始化或修复采用 `raw/` + `wiki/` 分层的 Obsidian Vault。项目真实目录是结构事实源；模板中的数量、领域和路径必须由当前 Vault 计算或填写，不能照抄其他项目。

如果同时提供 `AGENTS.md` 与 `CLAUDE.md`，推荐把它们作为同一 Schema 的两个入口：两份文件保存完全相同的内容，并在公共规则之外同时包含 Codex 与 Claude Code 适配章节。运行时只应用对应适配章节。

````markdown
# <Vault 名称> — LLM Wiki Schema

## 1. 角色与规则优先级

你是这个知识库的维护者。你的职责是读取原始资料、维护结构化 Wiki、回答问题并保持知识库健康。

规则优先级：

1. 用户当前明确指令；
2. 本文件公共规则；
3. 与当前运行时匹配的适配章节；
4. 页面或目录局部约定；
5. 工具默认行为。

如果 Vault 同时保留 `AGENTS.md` 与 `CLAUDE.md`，两份文件必须字节一致。修改任一文件时同步修改另一文件，并验证 SHA-256。

## 2. 架构与事实源

- **`raw/`**：不可变原始资料层。只读，不修改、移动、重命名或删除。
- **`wiki/`**：LLM 生成和维护的知识层。
- **`index.md`**：页面导航与索引统计。
- **`log.md`**：操作日志，仅追加。
- **`AGENTS.md` / `CLAUDE.md`**：Schema 入口。

当前 `raw/`、`wiki/` 的真实目录是结构事实源。Schema 负责记录稳定结构，不把偶然内容叶子固化成长期规则。

### 2.1 稳定层级登记策略

- 第 1–2 层：登记正式领域和主要业务分支；
- 第 3 层：登记长期稳定的业务分类；
- 第 4 层：仅登记满足以下任一条件的稳定功能目录：
  - `index.md` 中存在独立分区；
  - 包含多篇 Wiki 页面；
  - 后续路径选择必须依赖该分类；
- 课程名称、书名、日期会议、单页资料等内容叶子不逐项登记；
- 新目录出现时先检查真实结构，再判断是否进入 Schema。

## 3. 领域注册表

| 领域 | raw 路径 | wiki 路径 | 描述 |
|---|---|---|---|
| <领域1> | `raw/<领域1>/` | `wiki/<领域1>/` | <描述> |
| <领域2> | — | `wiki/<领域2>/` | <无 raw 层的提炼型领域描述> |

`registered_domain_count` 等于本表数据行数，不含表头和分隔行。新增领域时创建或确认对应目录，并同步更新本表；没有 raw 层时写“—”。

## 4. 命名与页面粒度

- 文件名使用描述性标题，并与页面标题一致；
- 日期前缀仅用于时序条目，例如 `2026-04-10 会议主题.md`；
- 一个文件聚焦一个概念；
- 不因标签规范化修改路径、文件名、标题、链接、图片嵌入或普通正文。

## 5. Frontmatter

每个 Wiki Markdown 页面必须从第一行开始使用 YAML frontmatter：

```yaml
---
title: "页面标题"
created: YYYY-MM-DD
updated: YYYY-MM-DD
domain: <领域名>
tags: [type/<类别>, domain/<名称>]
sources: []
status: draft | active | archived
---
```

- `title` 与文件名一致；
- `updated` 在正文、标签或来源元数据实质变化时刷新；
- `domain` 来自领域注册表；
- `tags` 是权威标签来源，不带 `#`；
- `sources` 指向 raw 目录或具体文件，目录路径以 `/` 结尾；
- 无 raw 层的提炼页可使用空数组，并说明推导基础。

## 6. 标签与链接

- 类型标签：`type/<类别>`；
- 领域标签：`domain/<名称>`；
- 标签片段中的空格使用 `_`，例如 `AI Live` → `AI_Live`；
- Inline tags 如存在，必须与 frontmatter 一致；
- 使用 `[[页面标题]]` 链接真实存在的相关页面；
- 使用 `![[文件名.ext]]` 引用 raw 附件；
- 图片引用可指定尺寸：`![[文件名|300]]`（宽度 300px）；
- 编辑页面时绝不删除已有图片引用，编辑前后须校验完整性；
- 优化页面时保留已有正文、图片嵌入和顺序，除非用户明确授权重构。

## 7. 图片 manifest 与批处理

图片密集页面或 raw 图片目录必须先建立 manifest：

| 序号 | 嵌入名 | 实际路径 | 来源匹配 | 状态/备注 |
|---:|---|---|---|---|

- Wiki 已有嵌入顺序是权威顺序；raw-only 图片按自然文件名排序；
- 图片重名、缺失、无法唯一定位或超出 declared sources 时必须报告，不猜测；
- 1–10 张：本地分析；
- 11–30 张：拆为 2–3 批；
- 31 张以上：总计最多 6 批（单波并发上限；总量更大时以波次推进，见 obsidian-llm-wiki SKILL「Subagent 批量分析」）；
- 返回结果必须逐项标明 manifest 序号或文件名，并在合成前完成对账。

## 8. 页面结构

Frontmatter 是必需结构。正文结构服从资料类型、已有页面和用户范围，常用顺序为：

1. 一句话摘要；
2. 主体内容；
3. 图片内容解析；
4. 资料总结；
5. 洞见与方法论；
6. 最佳实践或执行清单；
7. 金句精选；
8. `## 相关`；
9. `## 来源`。

正文排版遵循「排版规范」（H2 起始、层级不跳级、callout 表达特殊语义、图片默认不限宽），详见 obsidian-llm-wiki SKILL「## 排版规范」。

用户要求保留正文、图片和顺序并把补充放在最后时，新增正文只能追加在末尾；frontmatter 修复是唯一可置于正文之前的结构例外。

## 9. index.md 与统计

修改 `index.md` 时，同时刷新页首维护说明、页脚统计和索引健康行。

三个权威变量：

- `indexed_page_count`：可解析到真实 `wiki/**/*.md` 且去重后的索引页面数；
- `wiki_file_count`：实际 `wiki/**/*.md` 文件数；
- `registered_domain_count`：领域注册表数据行数。

三个健康变量：

- `missing_count`：未被可解析唯一索引覆盖的 Wiki Markdown 文件数；
- `broken_count`：无法唯一解析且不属于排除项的索引链接数；
- `duplicate_count`：同一真实 Wiki 页面在索引中的额外重复条目数。

统一模板：

```markdown
_统计：{indexed_page_count} 个已索引页面 | {wiki_file_count} 个 Wiki 文件 | {registered_domain_count} 个注册领域 | 上次更新于 YYYY-MM-DD_

> 索引健康：未收录 {missing_count} | Markdown 断链 {broken_count} | 重复条目 {duplicate_count}；`.canvas`、示例占位和 `raw/...` 链接不计入页面数。
```

只有条目、摘要、标签、分区、统计或健康状态变化时才修改 `index.md`。不得用 `wiki_file_count` 代替 `indexed_page_count`；数字必须由当次扫描生成。

## 10. 变更联动与日志

每次创建、修改、移动、归档或删除 Wiki 页面后：

1. 检查 frontmatter、sources、标签、链接和图片；
2. 检查 `index.md` 是否需要更新；
3. 检查两个 Schema 入口是否需要同步；
4. 完成索引与 Schema 验证；
5. 向 `log.md` 追加一次最终记录。
6. `log.md` 累积变大（超 `Read` 上限）时，追加用 EOF 直追（bash heredoc 或 PowerShell `Add-Content -LiteralPath -Encoding UTF8`），不为追加而整读旧内容。

Schema 或索引已经正确时记录“已检查，无需更新”，不要为制造操作痕迹而改写文件。

## 11. 工作流

### Ingest

只读检查 raw 来源 → 建立文件或图片 manifest → 确定领域与页面粒度 → 预处理或识图 → 创建带完整 frontmatter 的 Wiki → 检查相关链接和来源 → 必要时更新索引 → 验证 → 追加日志。

### Optimize

检查页面与来源 → 保存正文和图片顺序 → 按用户范围优化 → 更新 `updated` → 必要时刷新索引 → 验证无正文或图片丢失 → 追加日志。

### Query

读取索引和相关 Wiki → 必要时回溯 raw 来源 → 区分事实、推论和缺失信息 → 未经授权不写文件。

### Lint

检查 frontmatter、sources、图片、Wiki 链接、索引覆盖、统计健康、Schema 路径及双文件一致性。审计或只读任务只报告，不修复。

## 12. Codex 适配

- 使用当前可用的 Codex 工具；
- 只有用户或适用规则明确要求委派或并行时才使用 default agent；
- 项目脚本优先使用项目内固定 Python 运行时；
- 文件修改使用安全补丁机制；
- 遵守 Windows 删除、中文路径和 UTF-8 规则。

## 13. Claude Code 适配

- 使用项目声明的 Claude Code 配置、网关和 Agent；
- 图片读取使用项目声明的 image-reader；
- **读图前先做视觉通道顺序探测**（`Read` 单图 → 视觉理解 MCP（如 zai-mcp-server）单图）；第三方网关（如智谱 GLM、MiniMax）多模态下推可能未启用，`Read` 图片或仅返回 CDN 上传回执而无视觉内容，此时视觉 MCP 是首选兜底通道；两条通道都不可用才走降级（image manifest 照建、视觉字段标“视觉未识别”、基于已有文字提炼、不虚构），流程见 obsidian-llm-wiki SKILL「运行时与网关适配」；**在本节记录项目已验证的网关读图状态、视觉 MCP 通道状态与降级路径**；
- 工具调用与降级路径可以不同，但不得改变公共目录、领域、frontmatter、图片或统计规则；
- 不泄露密钥或本地敏感配置。

## 14. 安全限制

- 永不修改、移动、重命名或删除 `raw/` 内容；
- 不使用递归、通配符、管道、循环或目录删除；
- 物理删除 Wiki 文件必须来自用户明确授权，并一次处理一个明确文件；
- `log.md` 仅追加；
- 不覆盖用户未授权的内容；
- 不虚构来源、数据、引用或验证结果；
- 默认使用中文，除非用户明确要求其他语言。
````

## 初始化步骤

1. 扫描 Vault 的实际 `raw/`、`wiki/` 目录；
2. 按稳定层级策略填写模板，不登记内容叶子；
3. 填写领域注册表，不复制其他 Vault 的领域或数量；
4. 按你用的运行时保存到 Vault 根目录：Claude Code → `CLAUDE.md`；Codex / 其他 agent → `AGENTS.md`；
5. 多运行时并存则两份都存（完全相同）；单运行时单文件即合法配置；
6. 同时保留 Codex 与 Claude Code 适配章节；
7. 创建或检查 `index.md`、`log.md`；
8. 计算三个权威变量和三个健康变量，写入统一索引模板；
9. 如存在两个 Schema 入口，验证 SHA-256 完全一致。
